Prologue Overview

まえがき

相談された時点で決まっていたのは、体験のコンセプトだけだった。カメラの映像から人物の輪郭を切り出し、VR内のアバターに反映する。ソフトウェア側の実装は自分が担当した。実装の反復にはAIを使うvibe codingが効いたが、AIに任せきれなかったのは、実機と実データを見ないと判断がつかない部分、特にレイテンシに関わる設計判断だった。プロトタイプの見た目自体はすぐに作れても、それを破綻なく成立させるための下ごしらえには相応の時間がかかる。この記録は、その下ごしらえの中身を書き起こしたものである。

このパイプラインは、大きく分けて4つの実装からできている。ステレオカメラ本体とRaspberry Pi上でのH.264エンコード、PCへの独自UDP伝送、PC上でのRVM(Robust Video Matting)による人物マスキングと姿勢推定、そしてQuestの手指トラッキングとの合成を経てVRへステレオ描画するところまで。このどれか一つが欠けても体験は成立しない。以下では実装した順に、各段で何が問題になり、どう対処したかを章ごとに記録する。

Chapter 01 Latency Budget

各区間でのレイテンシの問題と対策

自分の動きとアバターの動きにズレがあると、体験は「操作している感覚」ではなく「映像を見ている感覚」に変わる[1]。区間ごとに問題の種類が違うので、対策も区間ごとに別々に打つ必要がある。

パイプラインは、カメラでの撮影からVRへの描画まで、性質の異なる4つの区間を通る。カメラからの伝送経路、ネットワークの伝送経路、PC側でのGPU推論の経路、そして描画までの経路。それぞれの区間で起きる遅延の原因は別物で、対策も別々に実装している。以下にまとめる。

区間ごとの問題と実装上の対策
区間起きる問題実装した対策

Chapter 02 Stereo Capture / Encode

ステレオカメラとRaspberry Piくん上のエンコード

映像の圧縮には、Raspberry Piくんのハードウェアエンコーダではなく、ソフトウェアのx264を使っている。

そもそもステレオカメラ自体、既製品を買ってきたわけではない。Raspberry Pi 5にRaspberry Pi用のカメラモジュールを2台取り付けて組み立てている。組み立てにあたっては、Raspberry Pi 5とカメラモジュールでステレオビジョンを構成した産業向けの事例（techietechnology.co.jp, 2025）を参考にした。専用のグローバルシャッターカメラや外部同期のハードウェアを使わなくても、Raspberry Pi 5であれば安価なカメラモジュール2台の映像を実用的な遅延で処理できる、という設計方針をそのまま踏襲している。

Raspberry Piくんにはハードウェアの映像エンコーダが載っているが、今回はlibx264によるソフトウェアエンコードを使っている。理由は、この体験では人物が写っている領域とそうでない領域とで圧縮の力配分を変えたい、つまりマクロブロックごとに量子化の強さを個別に指定したいのに、Raspberry Piくんのハードウェアエンコーダはあらかじめ用意されたレート制御モード（CBR/VBRなど）を選ぶだけのインターフェースしか持たず、フレーム内の特定の領域だけ量子化を変えるような細かい指定を外から差し込む余地がないからである。x264はソフトウェア実装なので、フレームごと・マクロブロックごとに量子化オフセットを自分で計算してAPI経由で渡せる。プリセットをultrafast・zerolatencyにし、Bフレームと先読みとCABACを切って、圧縮効率よりレイテンシを優先する設定も同時に組んでいる。

左右の映像は、1枚の画像の左半分と右半分にそれぞれの目を並べるSide-by-Side（SBS）方式[1]でまとめている。SBSにした理由は主に描画側にある。後段のVR表示シェーダーが1枚のテクスチャのアップロードだけで両目分をまかなえるため、伝送量とテクスチャ転送回数を抑えられる（詳細は第6章）。

もう一つ、実装として組み込んでいるのが、Raspberry Piくん上で動かす軽量なRVM（Robust Video Matting）推論による、圧縮の優先度づけである。PC側でVR描画用に使っているRVM（第4章・第5章で扱う本体のマスキングパイプライン）とは別に、Raspberry Piくん上でもCPU向けに調整したRVMモデル（rvm_mobilenetv3_fp32.onnx）を動かし、その出力から32×32タイル単位の重要度マップを作る、人物のタイルは量子化を甘く、背景のタイルは強くする、という設計でH.264のマクロブロックごとの量子化オフセットに反映させるコードは書いてある。ただし正直に書いておくと、これが会場の本番機で最後まで安定して有効化されていたかどうか、原稿を書いている自分自身、完全な自信があるわけではない。Raspberry Pi 5にカメラ2台とエンコーダとニューラルネットワーク推論を同時に載せて30fpsを維持するのは、要求としてはかなり欲張りな部類で、この部分が万一落ちても、その場合は単に「全タイル一律の優先度」にフォールバックするだけで、映像自体は途切れない設計にはしてある。

Chapter 03 Custom UDP Transport

独自のUDP伝送プロトコル

受信側は、フレーム番号が進んでいるものだけを常に採用する。

PCへの映像伝送にTCPを使わなかったのは、TCPが「ロスしたパケットを再送してでも順序通りに完全な形で届ける」ことを保証する仕組みだからである。この保証は、動いている自分の体をリアルタイムに映すという用途には合わない。少し前の完全な映像が届くより、今この瞬間の、多少欠けていてもいいから一番新しい映像が届くことの方が重要になる。そのため独自のUDPベースのフレーミングプロトコルを実装し、受信側は常に一番進んでいるフレーム番号のものだけを組み立てる設計にしている。

Ethernet上のパケットは、IPフラグメンテーションを避けるため1500バイトのMTUに収まるようチャンクに分割している。受信側はフレーム番号が後退しているパケットを破棄し、Raspberry Piくんの再起動などでフレーム番号が0に戻るような場合に備えて、連続して番号が後退したパケットが一定数（15回）続いたら基準をリセットするガードも入れている。

MetaPuppetPacket.cs のパケットヘッダ（56バイト、MTU 1500に収まるようチャンク化）
struct MetaPuppetPacketHeader {
  uint32  Magic;              // 'MPQ1'
  ushort  Version;            // = 1
  Flags   Flags;              // Keyframe / FecPresent / MaskPresent など
  uint32  StreamId;
  uint64  PacketSequence;
  uint64  FrameSequence;      // 受信側はこの値の前進だけを見る
  uint64  CaptureTimestampNs; // レイテンシ計測の起点
  uint32  ChunkIndex, ChunkCount;
  uint32  PayloadSize, FrameSize;
};

誤り訂正には、複数個の欠損を復元できるReed-Solomon系[1]ではなく、1フレームにつきXORパリティを1個だけ追加する単一パリティ検査符号（single parity check code）を使っている。理論上は2個以上のチャンクが欠けると復元できないが、パリティの計算がXOR一回で済み、実装も単純になる。1フレームの寿命がミリ秒単位のこの用途では、複数欠損に対応する複雑な誤り訂正の計算に時間をかけるより、次のフレームをそのまま受け取った方が結果的に速いと判断した。誤り訂正の手厚さ（FECのグループサイズ）も、第2章の重要度マップを再利用してタイルごとに変えている。

受信側は、直近何秒かでどれだけパケットが届いていて、どれだけ欠けていたかを10Hzで数え、その結果を送信側に送り返している。送信側はこれを見て、回線が詰まっていそうなら送出のペースを落とし、余裕がありそうなら戻す、という調整をしている。もう一つ、キーフレーム（それ単体で映像を復元できる特別なフレーム。詳しくは後述）が全部届く前に、次の新しいフレームに追い越されてしまった場合には、受信側から送信側へ1回だけ再送要求のパケットを送る仕組みも入れている。この再送要求パケットには、実装上KEYFRAME_NACKという名前をつけている[2]。

Chapter 04 GPU Segmentation Backend

TensorRTに置き換えて高速化をする

PC側の人物マスキングに使っているRVMの推論を、できるだけ速く、自然な見た目で動かすための最適化を重ねている。その一つが、GPU世代の変更で壊れた推論バックエンドを、cuDNN経由のCUDA EPからTensorRTへ乗り換えた経緯である。

MetaPuppetのPCVRパイプラインでは、ステレオカメラの映像から人物だけをリアルタイムに切り出すために、RVM（Robust Video Matting）というモデルをONNX[1]形式に変換したうえで、ONNX RuntimeのCUDA EP経由で動かしている。開発機を、巷で大変発火しやすいと噂のRTX 5070（Blackwell世代）のノートPCに切り替えるまでは、特に問題なく動いていた。Blackwellに切り替えたところ、いろいろな箇所でエラーが出るようになった。以下は、その経緯である。

RVMのrefiner部分にある、depthwise convolutionという種類の畳み込み層（4か所）が、cuDNN Frontend[2]の内部で失敗するようになった。エラーメッセージは短く、原因の手がかりはほとんど含まれていない。この手の一行エラーというのは、読んだ瞬間は情報が書いてあるように見えて、実際には「失敗しました」以上のことを何も教えてくれない、という性質を持っている。仕方がないので、乏しい状況証拠だけを頼りに推理を組み立てることになる。最初に立てた仮説は、「depthwiseはgroup convという特殊な形態だから、新しいGPU世代向けのカーネルがまだ用意されていないのだろう」というものだった。今にして思えば早計な仮説だった。

この仮説に基づき、対処法を考えた。GPUライブラリ側の修正を待つ、あるいはこの種類の層自体を使わないようモデルを設計し直す、という選択肢もあったが、それでは次のGPU世代でまた同じ問題に当たる可能性がある。そこで、失敗している4か所のdepthwise convolutionを、cuDNNの実行プラン選択を経由しない、もっと原始的な演算の組み合わせ（パディング→スライス→掛け算→足し算）に手作業で書き換えるという方法を選んだ。3x3のdepthwise convolutionは、パディング済みの入力から9通りのタップ位置ごとにスライスを切り出し、対応する重みを掛けて9個ぶん足し合わせる、という直接的な定義に従って書き下しただけの回りくどいやり方だが、数式は1項ずつ手で検算した。

書き換えた後も、元の演算とまったく同じ結果になっているかを確認する必要がある。2種類の精度で突き合わせた。1つは通常の32ビット浮動小数点（fp32）、もう1つは推論を高速化するために精度を落として使う16ビット浮動小数点（fp16）。結果は、fp32では出力のすべてが完全に一致し、fp16でも、人物のシルエットを表すアルファチャンネル（pha）と、直前までのフレームの情報を次のフレームに引き継ぐための内部状態（r1〜r4。RVMが動画のちらつきを抑えるために保持している、いわば記憶のようなもの）が完全に一致した。

これで解決したと、しばらくの間は考えていた。

問題の範囲を見誤っていた

パッチを当てて改めてテストすると、今度はdepthwiseでもなんでもない、通常の畳み込み層まで同じ症状で失敗した。エラーは「グラフの実行に失敗した」という趣旨の一行（CUDNN_FE failure 7: GRAPH_EXECUTION_FAILED）。cuDNN 9.xは個々の畳み込みを直接叩くのではなく、演算の組み合わせをグラフとして宣言してから、その実行プラン（どのカーネル・どのタイル分割・どのアルゴリズムで動かすか）をcuDNN Frontend自身に選ばせる設計になっている。今回の失敗は、この実行プラン選択のフェーズそのものが、この世代のGPU向けにまだ十分整備されていないことを示していた。

depthwiseが特別だったのではなく、cuDNN Frontendの実行プラン選択そのものが、もっと広い範囲で不安定だった。ノード単位で個別に迂回するやり方は、当たった箇所には確実に効くが、当たっていない箇所には何の効果もない。CUDA 12.8とcuDNN 9.8の組み合わせにアップグレードした結果、YOLOv3・YOLOv4・MobileNet V1が同じ症状で失敗するという報告も他所に見つかった。少なくとも環境固有の現象ではないことは分かった。

TensorRT-RTXへの乗り換えと、そこでの新しい失敗

方針を転換し、cuDNN経由のCUDA EPを避け、NVIDIAがクライアントRTX向けに提供しているTensorRT-RTX EPを使うことにした。GPU上に置いたテンソルの受け渡し先を、それまでCUDA専用の指定でハードコードしていたのを、どの実行プロバイダでも共通に使える指定へ書き直し、AUTO→TensorRT-RTX→CUDA→CPUという段階的なフォールバックも用意した。

TensorRT-RTXに切り替えると、cuDNN由来のConvの失敗は解消した。しかし今度は、RVM内部のResizeノード（バックボーンとrefinerの間で解像度を橋渡しするために、実行時入力であるdownsample_ratioに依存して動的にサイズを決めているもの）を、TensorRT-RTXのパーサーが解析できず、内部の形状チェックに矛盾がある、という趣旨の別のエラーで失敗するようになった。TensorRT系のパーサーは実行時に値が決まるResizeのサイズを扱いにくく、scales/sizes入力がグラフレベルの定数（initializer）でなければ解析できないという制約に、今回もそのまま引っかかった。

これには比較的すぐに糸口が見つかった。MetaPuppetは実際にはセッションごとに固定の解像度でしか推論しないため、downsample_ratioを実行時入力として渡す必要はそもそもなかった。モデル変換スクリプトを書き、この値をモデル内の定数として焼き込み、内部のResizeを完全な静的形状に置き換えた。

Resizeの問題は解消したが、今度はRVMの再帰状態r1〜r4をブロードキャストする部分で、「範囲外アクセス」という、モデル側の改造では対処できない、TensorRT-RTX側の内部の不具合に行き当たった。TensorRTのExpandは内部的にSliceレイヤーへ変換されることがあり、そこでの範囲外アクセスは、パーサーというよりビルダー側の不具合と見るのが妥当である。個別の失敗箇所をその都度モデル側で回避し続けるやり方には限界があることが見えてきた。

CPUフォールバックの確認と、最終的な実装

並行して調べていたGPU常駐CUDAパスは、例外すら発生させずに黙って失敗するという、輪をかけて診断のしづらい症状を見せていた。専用の診断APIを用意しても、Ort::Exception[3]（ONNX Runtimeが内部で投げるエラーの型）以外の何かによって失敗しているらしく、原因はまだ特定できていない。ここで一度、CPU推論への安全なフォールバックが確実に機能するかをUnity上で確認した。結果は「推論に成功したフレームが14、失敗して飛ばしたフレームが0、最終ステータスは正常」を意味するログ（FramesInferred=14, FramesSkipped=0, LastStatus=OK）で、画面上の人物クロッピングも正しく表示された。

現在の実装は、TensorRT-RTXではなく、通常のTensorRT SDK[4]（11.2.1系）のAPIを直接呼び出す経路を使っている。ONNXを完全な静的形状（batch=2、640×360または512×288の固定解像度、再帰状態r1〜r4のチャンネル数・空間サイズもすべて数値で固定）に特殊化し、onnx.checkerとshape inferenceを通し、CPU上で元モデルと特殊化モデルの出力（phaだけでなくr1〜r4も含めて）を突き合わせ、Unityを経由しないスタンドアロンの実行ファイルでエンジンのビルドを確認してから、GPUの描画バックエンド（Direct3D 11、詳しくは第5章）とCUDAとの相互運用コードに進む、という順序で検証している。

この過程でNVIDIAの開発者フォーラムを検索していたところ、Jetsonくんで同じRVMモデルをパースしようとして、まったく同じところでつまずいている同志の投稿を見つけた。世界のどこかに、同じ深夜に同じエラーメッセージと向き合っている人がいるというのは、地味に励みになる。その報告によれば、downsample_ratioの固定化だけでは不十分で、shapeに関わるテンソル[5]をINT64からINT32へ明示的にキャストしなければ、TensorRTのパーサーが"network input that is shape tensor must have type Int32"というエラーで落ちるとのことだった。この情報をもとに、モデル変換スクリプトにINT32化の処理を追加し、実装を完了している。

  1. ONNXは、PyTorchやTensorFlowなど別々の学習フレームワークで作ったモデルを、共通の1つのファイル形式に変換して保存するための規格。ONNXに変換しておけば、学習に使ったフレームワークに縛られず、ONNX Runtimeのような別の推論エンジンで実行できる。
  2. cuDNN Frontendは、NVIDIAが提供するcuDNN（GPU向けのディープラーニング演算ライブラリ）のC++/Python API層。個々の演算を都度呼び出す旧来のAPIとは異なり、演算をグラフとして宣言し、実行時にそのグラフに合う最適なカーネル（実行プラン）をライブラリ側に選ばせる設計になっている（NVIDIA cuDNN Frontend documentation）。
  3. ONNX Runtimeが内部でエラーを検知したときに投げるC++の例外クラス。通常はこれを捕まえればエラーの内容を文字列として取得できるが、今回のCUDAパスの失敗はこの例外を経由せずに（クラッシュでもなく、正常終了の顔をして）静かに失敗していたため、原因の切り分けが難航した。
  4. TensorRTには、データセンター向けGPUも含めて幅広い環境を対象にした従来からのTensorRT SDKと、GeForce RTXなどクライアント向けGPUに絞って軽量に配布できるようにしたTensorRT-RTXという、系統の異なる2つの実装がある。TensorRT-RTXはアプリに同梱しやすい代わりに新しく、パーサーの対応範囲がまだ狭い。今回はTensorRT-RTX側のパーサーの不具合を避けるため、対応範囲の広い従来のTensorRT SDKを直接使う経路に落ち着いた。
  5. TensorRTでは、テンソルの中身が画素値のような「データ」ではなく、別のテンソルの形状（サイズ）そのものを表す場合があり、これをshape tensorと呼ぶ。ONNXの標準的な整数型はINT64だが、TensorRTのパーサーはshape tensorについてINT32しか受け付けないため、明示的なキャストが必要になる。
Chapter 05 GPU-Resident Pipeline / Pose / Hand Tracking

マスキング、姿勢推定、手指トラッキングの合成

RVMとRTMPoseはGPU上に常駐して処理を続け、操作の判定はQuestの手指トラッキングが持つ。

体を切り出したあと、そのシルエットをVR内のアバターの動きに変換するには、関節や骨格の位置を推定する必要がある。ここではMediaPipeではなくRTMPoseを使っている。理由は、RTMPoseがRVMと同じD3D11[1]/CUDA相互運用の枠組みに乗り、CPUへ映像を戻すことなくGPU上に常駐したまま処理を回せるためである。RTMPoseは、RVMのマスクを常に受け取るわけではなく、目のID（左右）が一致していること、マスクが未来のフレームのものでないこと、許容ラグの範囲内であることを確認したうえで受け取る。この条件を満たさない場合はマスクを使わず、それでも体験自体が止まらないのは、Questのハンド・パームトラッキングが常にゲームプレイ上の正として扱われ、RVMやRTMPoseの結果とは独立して動いているためである。マスクと姿勢推定は、あくまで見た目の合成に使われるレイヤーであり、操作の判定そのものには使っていない。

GPU常駐パイプラインで徹底しているのは、CPUとの往復を発生させないことである。カメラから来たNV12[5]の映像は、D3D11のコンピュートシェーダーでリサイズ・色空間変換（BT.709）・正規化・NCHW[2]並べ替えまでを済ませ、CUDA相互運用のバッファへそのまま渡り、ONNX RuntimeのIoBinding[3]へ永続的に結び付けられる。ステレオの左右2枚はbatch=2としてまとめて1回の推論に投げ、再帰状態（r1〜r4）は目ごとに独立したレーンで管理し、バッチ全体が成功したときだけ状態を入れ替える。推論結果のアルファチャンネルは、D3D11側に戻ってから境界のぼかしと時間方向のEMAを経て、そのままシェーダーに渡る。この経路では、ソース映像のホストからデバイスへの転送も、マスクのデバイスからホストへの転送も、バイト数はゼロになっている。

同じ組み合わせ（リングバッファのスロットと再帰状態バンクのアドレスの組）に対してはCUDA Graph[4]のキャプチャを試み、成功すればその分の呼び出しオーバーヘッドを削れる。キャプチャが失敗する場合は通常のIoBinding経由の呼び出しに自動でフォールバックする。リングバッファも2スロットに留め、常に最新のフレームが処理対象になるようにしている。

  1. Direct3D 11。Windows上でGPUに描画命令を出すためのAPIの一つ。Unityの描画バックエンドとしても使われており、映像デコーダの出力やRVMの推論結果は、このDirect3D 11が管理するGPU上のメモリ（テクスチャ）としてやり取りされる。CUDAとの相互運用は、このDirect3D 11側のメモリをCUDA側からも直接読み書きできるようにする仕組みを指す。
  2. 画像を並べるバイト順の規約の一つ。N（枚数）→C（色チャンネル数）→H（縦）→W（横）の順に並べる、という意味で、ニューラルネットワークの推論エンジンが入力テンソルとして受け取る標準的な並び方である。これに対し、通常の画像ファイルやシェーダーはH×W×Cの順（HWC、1ピクセルごとにRGBが並ぶ）で扱うことが多く、推論に渡す前にこの並べ替えが必要になる。
  3. ONNX Runtimeの機能の一つ。通常は推論のたびに入出力データをCPUとGPUの間でコピーするが、IoBindingを使うとGPU上の特定のメモリアドレスを入出力として固定でき、コピーを省略できる。
  4. 映像の色を輝度（Y）と色差（UV）に分けて記録する形式の一つ。色差は輝度の半分の解像度に間引かれており、その分データ量が少なくて済むため、映像のデコード・エンコードで標準的に使われる（第6章で改めて触れる）。
  5. 推論1回につき、実際にはGPU上のカーネル呼び出しやメモリ操作が何十個も連なって実行されている。CUDA Graphは、この一連の呼び出しを「ノードとその依存関係」というグラフ構造として一度だけ記録（キャプチャ）しておき、以降はCPU側から1回の呼び出しでそのグラフをまるごと再生できる仕組みである。「グラフ」という名前は、この依存関係の構造そのものを指している。
Chapter 06 VR Display Shader

SBSシェーダーで両目・色変換・合成をまとめて処理する

1枚のテクスチャで、両目の描画・色空間変換・人物合成の3つを片付ける。

VRヘッドセットへ表示するシェーダー（MetaPuppetSbsUnlit.shader）にも、伝送量を減らすための工夫を入れている。第2章で触れたSBS（Side-by-Side）パッキングは、Unityのシングルパス・インスタンシング（1回の描画コールで両目分を処理する方式）と相性がよい。1枚のテクスチャをGPUに一度アップロードするだけで、左右それぞれの描画時にUV座標のUの半分だけをずらして読むことで両目分をまかなえるため、両目ぶん別々にテクスチャを転送・バインドする必要がなくなる。

MetaPuppetSbsUnlit.shader　目ごとのUV選択
float2 uv = float2(
    eyeUv.x * 0.5 + saturate(eye) * 0.5,
    eyeUv.y
);
// eye は unity_StereoEyeIndex（シングルパス・インスタンシング時）
// または _MetaPuppetEyeIndex（テスト時の明示指定）

このシェーダーはさらに2つの処理を同じフラグメントパスに詰め込んでいる。1つは、デコード済みのRGBAだけでなく、デコーダが直接出力するYUV NV12[1]平面（輝度R8プレーンと色差RG8プレーン）をそのまま受け取り、BT.601[2]の変換式でシェーダー内部でRGB化する経路。これにより、CPU側で色変換をかけるステップを省略できる。もう1つは、RVMの出力アルファを外部マスクテクスチャとして受け取り、クロマキー・マットキーとの切り替えも含めて背景合成をこのパスの中で完結させている点である。両目の描画、色空間変換、人物合成という3つの処理を1つのUnlitフラグメントシェーダーにまとめているのは、描画コール数とテクスチャアップロード回数を最小限に絞るためである。

  1. 映像の色をRGBではなく輝度（Y）と色差（UV）に分けて記録する形式の一つ。人の目は色の変化より明るさの変化に敏感なため、色差の解像度を輝度の半分に間引いてもほとんど劣化して見えない。この間引き分だけデータ量を減らせるため、映像のデコード・エンコードでは標準的に使われる。
  2. YとUVの組をRGBに変換するための係数を定めた規格。放送や配信の分野ではBT.601（標準画質向け）とBT.709（ハイビジョン向け）の2種類が広く使われており、係数がわずかに異なる。どちらの規格の係数を使ったかによって色味が変わるため、デコーダ側とシェーダー側で規格を揃える必要がある。
Epilogue Summary

あとがき

ここまで記録した対策は、単体で見ればどれも小さなチューニングにすぎない。カメラ側の重要度マップを圧縮とFECの優先度づけに使うこと、受信側が常に最新フレームだけを採用すること、GPU常駐パイプラインでCPUとの往復をゼロにすること、SBSパッキングで両目分のテクスチャ転送を1回にまとめること。これらは第1章の表に挙げた4つの区間それぞれに対する、個別の対策として実装している。1つ1つは地味で、単体で自慢できるような技術ではない。ただ、この地味な対策を4区間ぶん積み上げて、なおかつどこか1箇所でも手を抜くと体験全体が「操作している感覚」から「映像を見ている感覚」へ転落するというのが、この手の実装の面倒なところだと思う。

特に、人物の重要度マップという1つのシグナルを、符号化の量子化と誤り訂正の両方に使う設計について、既存の特許を調べてみたところ、量子化と誤り訂正を組み合わせたもの（例えばNokiaのUS7206456B2）はあっても、そこにレイテンシ・バジェットに応じた送信ペーシングまで一緒くたに突っ込んだ例は見当たらなかった。特許調査などという柄でもない作業を深夜にやっていたのは、単に「これ、もしかして誰もやっていないのでは」という予感が当たっているかどうかを、自分の手で確かめたかっただけである。この記録が、同じようにGPU世代交代に殴られている誰かの深夜の検索に、たまたま引っかかれば幸いである。
